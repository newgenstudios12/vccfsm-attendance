# Member IDs and physical ID requests

Members open **Digital ID** in the navigation to see their current member record, permanent number, photo, attendance QR, and personal details. Linked members can submit a **Request for physical ID**, view its status, and cancel a pending request. Admins and pastors use **Church Management → ID Requests** to prepare IDs, add a note for the member, and record pickup.

`members.member_number` is a unique, immutable, six-digit public identifier. The database assigns it to future inserts using a private sequence and ignores numbers supplied by a client. Numbers remain unchanged when personal information, area, status, or ministry changes. Sequence gaps after failed inserts, rolled-back transactions, or deletions are expected; numbers are never recycled. `members.id` remains the relational UUID and `member_code` remains available for existing printed QR codes. All five active attendance scanners accept both generations of QR and UUIDs. Member search accepts both public numbers and legacy codes.

## Current information

The Digital ID queries the member record when opened, after local member/photo changes, when the tab regains focus, and every 30 seconds while visible. It stores no separate ID snapshot. Saved photo and personal information changes therefore appear automatically. Pending form notes survive refreshes, and background refreshes do not interrupt an admin reviewing a request. Member full names are generated by the database from first and last name; edit forms show that generated value as read-only and leave it out of update payloads.

## Request permissions and lifecycle

- A signed-in user can request an ID only for their linked member record and view their own requests for that record.
- One open request per member is enforced by a partial unique index, including simultaneous submissions.
- Only admins and pastors can read the full queue or add fulfillment notes.
- Pending → Printing → Ready for pickup → Collected. Admins/pastors can decline a pending request or cancel an open request. A member can cancel their own pending request.
- Closed requests cannot be reopened. A new request may be submitted after a previous request is collected, declined, or cancelled.
- Original requester, member, creation time, request notes, and request UUID cannot be reassigned during review.
- The request table uses row-level security; anonymous access is revoked. Internal trigger functions use the caller's privileges, a fixed empty search path, and no public execution grant.
